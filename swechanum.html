A note on "first": FTC teams have built swerve drivetrains for years on the legacy Control Hub/REV ecosystem — this isn't the first swerve chassis in FTC history. What's genuinely early here is running swerve on FIRST's brand-new Systemcore/Motioncore/A301 stack, which is still Alpha/Beta hardware being tested ahead of a planned 2027–28 season rollout. Swechanum appears to be among the first working swerve builds on that new platform.
The Hardware

A completely new control system, from the ground up

Systemcore replaces the Control Hub as the compute/networking brain of the robot. Motioncore replaces the Expansion Hub as the power and CAN distribution hub for motors. Together with the A301 brushless motor, they form FIRST's unified hardware platform — designed to eventually run the same WPILib software stack across both FRC and FTC.

Runs the robot program, dashboard/web configuration, networking, and the software environment. Provides USB, Ethernet, Wi-Fi, I²C, PCIe, and multiple CAN buses, plus Smart I/O for lights and sensors.

Power · CAN Distribution

Motioncore

The motor hub. An 18V battery dock powers it directly; a Bridge port sends power and CAN back to Systemcore. 20 point-to-point device ports carry CAN + power for A301 actuators or smart sensors, plus 3 quadrature encoder ports.

The Robot

Swechanum: flip it over, learn the next drivetrain

One chassis, two faces. Flip it one way and it's a conventional 4-wheel mecanum drive — the approachable entry point. Flip it the other way and it's a square swerve drive with independently steered corner modules. Same code stack, same hardware family, two very different control problems.

Teaching dimensionMecanum sideSwerve side
Control complexityLow / mediumHigh
Mechanical steeringNoneYes — per module
Basic omni motionWheel mixingWheel vectors + steering
Feedback control needOptional for basic drivingCore to steering
Programming progressionFast first successMore math, modular control
Best teaching useFoundations + driver controlKinematics + closed-loop systems

The point isn't to crown a winner — it's to give students a physical reason to understand the code behind both. In the current build, the mecanum side is intentionally unpowered (it would need 4 more A301s); all eight drivetrain motors — one drive, one steering, at each of the four corners — live on the swerve top.

The swerve pod, in miniature

Each corner module is two A301s: one steering motor mounted directly at the module's center of rotation, and one drive motor powering the wheel through a fully geared transmission — two 1:1 spur stages feeding an offset bevel set for an overall 3.1:1 wheel reduction.

This single pod is the smallest useful unit for teaching steering before layering on full robot kinematics. The current implementation runs open-loop, similar to a stock FRC swerve module, with closed-loop steering as the next milestone.

Programming Deep Dive

From a joystick to four independent wheel angles

Swerve control is fundamentally a coordinate transform: a single desired chassis motion (drive + strafe + rotate) has to become four independent (angle, speed) pairs — one per module — recomputed every control loop.

01
Chassis command
Gamepad axes → forward, strafe, and rotation velocities (field- or robot-centric)
→
02
Module vectors
Translation vector + rotation-induced vector summed at each module's (x, y) offset from center
→
03
Angle + speed
Each module vector converted to a target heading (atan2) and magnitude (hypot), then desaturated
→
04
Local pod control
Steering PID drives the A301 to the target angle; drive A301 is commanded to target speed

A301 motor object — real API from the Systemcore repo (REVLib)

// Create an A301 on Motioncore channel 0. CAN ID defaults to 3. A301 steerMotor = new A301(CANBusMap.CAN_D0); // Same port, non-default CAN ID of 5 A301 driveMotor = new A301(CANBusMap.CAN_D1, 5); // Command by velocity (RPM), relative position, or absolute position driveMotor.setVelocity(100); steerMotor.setPosition(5); // multi-turn steerMotor.setAbsolutePosition(0.4, false); // single rotation, 0–1 steerMotor.setAbsolutePosition(-0.4, true); // shortest-path wraparound // Signals report validity alongside the value — always check before trusting them Signal<Double> velocity = driveMotor.getEncoderVelocity(); if (velocity.isValid()) { odometry.update(velocity.get()); }

Why "shortest path" matters for a steering pod

// Naive steering: always drive straight to the commanded angle. // Problem — going from 179° to -179° looks tiny to the driver // but is a near-360° spin to a motor that doesn't know it can go the other way. // Pod optimization (module 05 below) — instead: // 1. If the target angle is more than 90° from current heading, // flip the target 180° and invert the commanded wheel speed. // 2. Steer to the flipped angle instead — same net wheel direction, // much less rotation. // setAbsolutePosition(angle, continuousInput=true) is what implements // the wraparound half of this in the A301 API itself.
Curriculum

Flip. Code. Compare.

The workshop sequence used to build up Swechanum's software, one control concept at a time — students build confidence on the mecanum side before the swerve side demands closed-loop thinking.

01

Mecanum code

Motor direction, gamepad input, normalization, strafe/rotate tests.

02

Field-centric mecanum

IMU heading, coordinate rotation, driver-oriented control.

03

Single swerve pod

Angle feedback, steering PID, wheel speed, wraparound handling.

04

Pod optimization

Shortest-path steering, speed inversion, deadband tuning.

05

Swerve kinematics

Translation + rotation vectors, module states, desaturation.

06

Drive & compare

Flip the chassis, run equivalent maneuvers, discuss tradeoffs.

Getting It Working

Alpha hardware doesn't have a one-click setup

The stock Systemcore + Motioncore + A301 path wasn't enough on its own. Getting to a usable, repeatable test rig meant reinstalling pieces, matching versions, and validating the A301s independently rather than trusting the examples.

1

Default setup failed

  • Started with the normal Systemcore + Motioncore + A301 setup
  • Open-loop control could move motors fine
  • Encoder position control acted wrong or became unreliable until later fixes
2

Reinstalled + updated

  • Reinstalled/reflashed Systemcore after updates behaved inconsistently
  • Updated A301 firmware and matched REVLib/firmware versions
  • Used REV Hardware Client 2, reboots, and power-cycles to recover bad states
3

Tested our own way

  • Built small, isolated A301 tests instead of relying only on samples
  • Separated working throttle control from failing position-control paths
  • Debugged software/API issues with mentor support to get the setup usable
Bottom line: it was not a one-click stock setup. The system became usable by treating it like alpha hardware — reinstall, update, test one layer at a time, then document what worked and what didn't.
01 · Software

Absolute encoder state

Expected
Default absolute range of −0.5 to 0.5 rotations
Observed
After pushing new code, the value could keep increasing instead of wrapping inside the absolute range
Fix used
Unplug and reconnect the affected motor after deploying new code — the issue only appeared after a fresh code push
Lesson: code deployment could leave motor/encoder state in a bad condition, so power-cycling the motor became a permanent step in the test procedure.
02 · Mechanical

Battery + switch packaging

No CAD provided
The mount had to be designed around the physical hardware instead of an accurate model
Access conflict
Making the battery easy to remove tended to bury the switch; keeping the switch reachable made the battery awkward to remove
Preferred layout
Ideally the battery would lie flat instead of standing 90° upright — but that pushes the switch deeper into the robot
Lesson: serviceability became part of the mechanical design, not an afterthought.
